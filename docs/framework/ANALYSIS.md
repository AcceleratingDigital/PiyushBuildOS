# Crosswalk: Framework A ("AI-Assisted SDLC: Ways of Working", Accelerating Digital v1.1) ↔ Framework B (PiyushBuildOS / hOS live process)

A = top-down, multi-human team playbook (GitHub Issues/Projects, sprints, PR review).
B = bottom-up, single-human + AI-agent pipeline (Asana free-tier intent-SSOT, git build-SSOT, trigger-script gates, built from 15 logged process incidents).

## 2. CONCEPT CROSSWALK

### Human-in-the-loop: Approve / Verify / Own vs B's role boundaries + charter
- A's **Approve** (PR approval, go/no-go, scope acceptance) maps in B to: Piyush tagging `status-ready-to-build` (requirements approval), Piyush's "ship vX.Y.Z" (release go/no-go), and the **iOS device-confirmation gate** ("Piyush explicitly confirms ✅"). These are real Approve events — but B has **no Approve between coder and merge**, where A demands one (plus a second reviewer for security-relevant changes).
- A's **Verify** (check AI output against source) maps to B's strongest idea: QA's **"self-reports rejected"** rule and "independent audit verification" (re-run the coder's claimed search and confirm the count) — codified *because* incident: "QA accepting coder self-declared audits → v0.6.11 shipped with same crash class." B's Verify is more operationalized than A's.
- A's **Own** (named owner of a check) maps to B's role files + oversight charter, where each MUST-NOT cites the incident that created it. A's ownership is recorded in CODEOWNERS/checklist fields; B's ownership is behavioral and enforced by role separation + the charter's "no file citation = no claim" rule.
- Net: B implements A's Verify better and A's Approve worse. A's "Decisions AI never makes" list (merging, releasing) is **contradicted by B's auto-merge**; B compensates only at the release gate.

### Traceability: FR-IDs vs Asana GID + branch-name linkage
- A: permanent `BR-/FR-/NFR-` IDs; BR→FR→TSD→Epic→Story→Task→PR→Tests→Release chain; CI job regenerates `traceability.md` and **fails** on gaps, validating issue types.
- B: Asana task GID ↔ `feature/{slug}` branch (GID-tied canonical name, banned `-v2/-fresh` suffixes) ↔ one PR per feature ↔ scope doc on the branch ↔ release notes; the **drift-audit cron** and daily S-S-D drift checks are B's traceability enforcement. Gate contracts verify branch-name-in-notes and scope-doc-exists before dispatch.
- Verdict: B's linkage is **coarser but actively audited** (drift audit catches Asana/git/reality divergence — something A's CI check doesn't do); A's is **finer but passive per-merge**. B cannot answer "which FR does this test cover?" because requirements carry no IDs and tests mostly don't exist. A wins on audit evidence; B wins on drift detection between intent and reality.

### DoR/DoD vs BUILD READINESS + gate contracts
- A's DoR: approved FR + merged TSD section, Gherkin ACs, estimates, designs, ai-suitable rating. B's **BUILD READINESS** section: dependencies, parallel-safety, risk level + reason, S/M/L scope, branch — a subset, minus testable ACs.
- A's DoD: merged with green CI, tests passing, coverage gate, docs updated, scans clean. B's **gate contracts** are a DoD expressed as machine-validated preconditions per transition ("no soft passes" → `status-blocked` + Slack alert). B's DoD is *stricter in form* (enforced, binary) and *weaker in substance* (no coverage, no scan, no test-run requirement — "branch has new commits" is literally a Coder→QA gate input).
- Net: A defines quality outcomes; B defines process preconditions. Neither has both.

### Sprints/ceremonies vs event-driven continuous pipeline
- A: two-week sprints, 7 ceremonies, AI-prepared, humans decide. B: zero ceremonies — trigger.sh direct chaining, serialized one-task queue, delta-only reporting ("silence = healthy"), lease-based `status-in-progress` with 30-min stall reversion, pause protocol when the human works manually.
- B's event-driven model is genuinely superior for a pipeline whose "team" is cron jobs; A's ceremonies have no humans to fill them. But A's refinement/planning is where scope negotiation happens; B substitutes the DECISION_PATTERN one-at-a-time decision sessions — adequate for one owner, unscalable to a team.

### Metrics: DORA/flow/quality/AI-effectiveness vs pipeline-stats
- A: DORA five metrics, flow (cycle time, PR size, review wait), quality (escaped defects, coverage, flaky count, security findings), traceability %, AI effectiveness incl. **human-catches-by-phase**.
- B: `pipeline-stats/{slug}.json`, watchdog-state.json, branch-cleanup log, drift-audit output, human-testing session summaries (pass/bug/feature counts per release), branch-count drift alerts.
- Overlap is thin. B measures the *pipeline* (stalls, drift, stalls-by-class); A measures the *product delivery* (lead time, failure rate, escaped defects). B has no escaped-defect metric despite shipping multiple crashing releases — the data exists in human-testing session logs and is never aggregated. A's "human catches by phase" concept exists implicitly in B's incident corpus gap classes but isn't quantified.

### AI governance: ADR-0002/MCP allowlist/data classification vs model matrix + role guardrails
- A governs *what AI may touch* (approved tools per data class, MCP allowlist as ADR change, OIDC for CI agents, prompt injection warnings, access lifecycle, quarterly review). B governs *which model does which job* (per-role CLI + model + escalation, MODEL PINs that win over dispatch instructions, LiteLLM proxy centralization) and *what agents may never do* (role guardrails, charter MUST-NOTs).
- B has nothing answering: data classification, redaction before AI sees sources, tool/MCP allowlist review, credential offboarding, prompt versioning. Its known "PII in repo" issue is the receipt. Conversely A has nothing answering B's model-pin drift enforcement or per-role escalation paths — A says "match the model to the task" (AI cost section) but has no mechanism to pin or audit it.

## 3. GAP LIST

### What B genuinely lacks that A requires
1. **Permanent requirement IDs + PR-reviewed requirements (docs-as-code).** Specs live in Asana notes (mutable, single-copy, no diff review) plus a scope doc on a feature branch. A's Principle 3 ("changed only by pull request, reviewed like code") has no B equivalent; B's contract artifact cannot be diffed or attributed.
2. **ADRs as first-class per-decision records.** DECISION_PATTERN is a mega-doc with manually maintained supersede markers (coder.md lesson 19 shows supersede discipline failing in practice — stale references caused a dedicated cleanup task). No `docs/adr/` log with status.
3. **Architecture/NFR review.** No availability/RPO/RTO/tenancy/async/cost checklist anywhere. Security review is per-diff (reviewer-security checklist) — real threats (member scoping, path traversal) get caught, but design-level review ("which decision meets each NFR?") never happens. B2's SQLite→pgvector reversal is what A's Phase 2 checklist is designed to prevent.
4. **Test automation gates.** qa.md: test targets are stubs; "No real test coverage exists for any feature as of 0.5.0." No coverage threshold, no 0-failing-tests gate, no contract tests, no regression suite. Every release re-derives correctness through QA agents + human testing — which is why the same crash class shipped twice (v0.6.11).
5. **CI on the PR.** The QA agent is the CI: non-reproducible, model-dependent, no SBOM/provenance, no pinned environment. A's supply-chain evidence (SBOM, signed attestation) is absent — ironic for a process that notarizes every DMG.
6. **Request ledger / change accounting.** Feature requests from testing land in Asana, but nothing guarantees every stakeholder request resolves to an FR, a merge, or a recorded rejection. A's request-ledger exists precisely because "the BookIt waitlist request was lost" — B has the same exposure with no ledger.
7. **Product postmortems.** Incident corpus covers *process* failures superbly (15 incidents, 7 gap classes); shipped product failures (4 crashing iOS versions, CloudKit guard silently breaking sync "across all versions") get bug tasks only — no blameless postmortem with action items and no Sev classification.
8. **DORA/escaped-defect metrics.** No lead-time, change-fail-rate, or escaped-defect measurement despite all the raw data existing in Asana tags and git history.
9. **Data classification/redaction + access lifecycle.** PII-in-repo issue outstanding; no classification scheme; no offboarding checklist (moot-ish solo, real if agents' tokens leak).
10. **Documentation freshness / spec-drift check.** Per-feature docs gate exists, but no periodic specs-vs-code drift audit (coder.md lessons 15–21 are an entire taxonomy of doc-drift failures discovered manually).
11. **Fast-track lane.** Trivial changes pay full pipeline toll; B's own gate contracts could cheaply define a small-change lane and doesn't.

### What A lacks that B learned the hard way
1. **Machine-checkable gate contracts.** A's gates are prose ("exit gate: approvals + green checks") interpreted by humans; B validates REQUIRED inputs per transition and hard-fails to `status-blocked`. For AI-executed processes, prose gates are unenforceable.
2. **Incident corpus with gap-class taxonomy.** A has per-incident postmortems; B classifies failures into 7 recurring classes (role ambiguity, tool bypass, concurrency, state hallucination, external-system discipline, layer separation, branch hygiene) and reviews the corpus monthly for pattern recurrence. A's retrospective is a ceremony; B's corpus is a dataset.
3. **Human-testing gate as a pipeline stage** — a dedicated agent that reads the *published docs* as the definition of "working as intended," walks the owner feature-by-feature, and files PASS/BUG/FEATURE verdicts with diagnostics attached. A's UAT is one checkbox in Phase 8; B's is the release-defining seal plus a standing feedback intake mechanism.
4. **Device-confirmation / multi-platform release gate.** "VALID in ASC ≠ releasable" — release completes only when all platform builds install, launch 10+ seconds on real hardware, and the human confirms. A's cloud-shaped playbook has no concept of artifact-level, per-platform completeness (and A's Phase 7 resilience testing never touches "does the shipped binary run").
5. **Write-back rule + cross-surface parity.** A assumes one repo = one shared memory; B learned that multiple agent surfaces (cron, GUI, Slack) drift and codified: write learnings to the shared file *before finishing your turn*, log actions to STATUS.json before responding, never reconstruct state from conversation. A has nothing for agent-to-agent memory coherence — its first multi-agent deployment would re-live B's v0.6.4/v0.6.5 crash chain ("stale context files caused it").
6. **State-hallucination guardrails.** "State claims require a cited file path or API response IN the answer"; single status point (STATUS.json schema 2); incident #11 was an agent looping all night on a hallucinated filename. A's HITL model never contemplates the *reviewer* being an agent that misremembers state.
7. **Codified role boundaries with incident receipts.** A's roles table says who owns what; B's charter says what each actor MUST NOT do and cites the incident that proved it ("violated Aug 22/23/30 — incident #1"). The negative-space definition is what survives contact with agents.
8. **Three-layer separation.** Product repo / process repo / runtime-state-not-in-git, with one-writer rules per layer. A's "one repository is the SSOT" would have produced B's incident #13 (runtime state git-tracked in two repos, drifting) on day one.
9. **Concurrency discipline for agents.** Staggered crons, lock files, lease-based statuses with stall detection, one-writer-per-resource, queue depth 1, pause protocol when the human is working. A has no concept that two agents can race.
10. **Canonical-tool bypass guardrails.** "DMG = package-release.sh only. No exceptions. Verify by mounting." A says "no manual changes to production" but has no artifact-verification step; B's incidents #2, #8, #9 are all bypass-shaped and A's process would not have caught any of them.
11. **Delta-only reporting.** "Never report 'no changes.' Silence = healthy." A's ceremony cadence institutionalizes noise; B's alert rules (only 🚧/✅/🚨/🚀) keep a human-in-the-loop sustainable.
12. **Branch hygiene automation.** Delete-on-merge as a mandatory coordinator step, banned branch-name suffixes, unmerged-branch drift alert (>5), deletion log with tip SHAs for forensics. A's rule is "delete the branch" in one line of Phase 6 with no enforcement — B accumulated 350 branches proving that's insufficient.

## 4. MIGRATION FEASIBILITY

### (a) Adopting A onto a solo + AI-agents setup **as-is**: **2/5**
A's load-bearing core (spec-before-code, traceability, PR gates, DoR/DoD, AI governance) ports fine and would fix B's three biggest deficits (IDs, coverage gates, CI evidence). But roughly half the playbook is people-shaped ceremony with no humans: sprints, standups, refinement meetings, backlog planning, second human reviewer, quarterly access reviews, "review two PRs from others before your first merge." The second-reviewer rule is not just unstaffable — it conflicts with the automation that makes B viable at all (auto-merge is what lets one human supervise a pipeline). Running A as-is means either a human simulating a team (rubber-stamp approvals, worse than no gate because it *looks* governed) or silent non-compliance. Adoption after stripping ceremony and substituting agent-executed verification: 4/5. As-is: 2/5.

### (b) Adopting B onto a multi-human team **as-is**: **2/5**
Three hard blockers. First, **auto-merge on AI security pass** — no team will accept an AI reviewer as the sole merge authority, and A is right about this even though B's QA/review discipline is more rigorous than most teams'. Second, **serialized one-task pipeline with queue depth 1** — built for a single CloudKit single-writer constraint and one machine; it would idle five developers. Third, **Asana free tier as intent-SSOT** — one project, tags-as-state, specs in task notes: no per-person assignment workflow, no hierarchy, no audit trail a second stakeholder can trust; the "notes are the contract" rule assumes everyone reads every task. What transfers beautifully and teams should steal regardless: gate contracts, incident corpus, role MUST-NOTs with incident citations, write-back rule, device-confirmation-style release gates, delta-only reporting. The framework's *governance layer* is team-ready; its *throughput and tooling layer* is solo-shaped.

### (c) Converging on one unified model: **4/5**
The skeletons are already isomorphic: both are gated pipelines (A's phases ≈ B's stage map), both are spec-before-code, both believe "automate the gate" (A Principle 7 ≈ B's trigger scripts), and both already converged on evidence-over-self-report (A's Verify vs B's "self-reports rejected"). A convergence is mostly re-plumbing, not re-design: (1) A's requirement IDs + PR-reviewed docs become the intent layer; (2) B's gate contracts become the enforcement layer for A's phases (write each of A's exit gates as a machine-checkable contract); (3) B's incident corpus + A's postmortems merge into one corpus with A's severity classes and B's gap classes; (4) A's ceremonies shrink to decision sessions (B's DECISION_PATTERN format) + a monthly metrics/corpus review. The genuine costs: B must build real CI + test coverage (weeks of work, not process change), and A must accept agent-executed verification with contractual evidence instead of human eyes on every diff. Feasible; the blocker is engineering effort, not conceptual incompatibility.

### Load-bearing vs ceremonial

**Framework A — load-bearing (cannot drop):**
1. Spec-before-code + Definition of Ready (the anti-"vague prompt" spine).
2. Permanent requirement IDs + CI-enforced traceability chain (the audit evidence).
3. Human Approve on merge and release — *especially* for security-relevant changes (the one place B is genuinely unsound).
4. AI governance data-classification/redaction (the PII lesson B hasn't learned).
5. Test/coverage gates in CI (B's biggest engineering gap).

**Framework A — ceremonial (droppable):**
1. Two-week sprints + standup/refinement/planning ceremonies.
2. Backlog YAML + sync-script mechanics (GitHub-API-specific).
3. 400-line PR sizing guidance and PR service levels.
4. Estimate/capacity/planning-poker apparatus.
5. Pairing/junior-development practices (no juniors in a solo+agents shop).

**Framework B — load-bearing (cannot drop):**
1. Gate contracts (machine-checkable, fail-to-blocked, "no soft passes").
2. Role boundaries + oversight charter, backed by the incident corpus and gap-class taxonomy.
3. Human-testing / device-confirmation release gate (the final seal on real hardware).
4. S-S-D discipline: single status point, write-back rule, cross-surface parity, state-claims-cite-files.
5. Multi-platform release gate + mandatory smoke test + canonical-tool-only packaging with artifact verification.

**Framework B — ceremonial/droppable (in a team context):**
1. One-task-at-a-time serialization (a single-machine artifact, not a principle).
2. Asana-free-tier-as-intent-SSOT specifics (tags-as-state-machine, GIDs in /tmp).
3. Dual-session Slack/GUI parity mechanics.
4. Machine-specific gate checks (pbxproj integer greps) — generalize into an artifact-manifest check.
5. The requirements-branch-as-state-log checkout topology.

## 5. TOP 10 CONCRETE TENSIONS

1. **"Author never merges own PR / second reviewer" (A Roles table, Phase 6) vs auto-merge on security-pass (B SHARED-CONTEXT § "Event-Driven Pipeline": "PRs merge when security reviewer passes (no human gate)").** The single sharpest conflict. A says an AI review never counts as approval; B's only merge approver *is* an AI. B's mitigation (evidence-citing QA, three reviewers, human release gate) is real but does not satisfy A's rule — and A's rule exists to stop exactly the failure B's incident corpus shows agents committing (self-reported audits, hallucinated state).
2. **Two-week sprints + ceremonies (A "Ceremonies, cadence and metrics") vs event-driven continuous chaining (B trigger.sh, serialized queue, delta-only).** A's planning horizon and capacity math have no place to land in a pipeline that starts the next stage the moment the previous one fires; B's throughput model has no place for sprint goals, mid-sprint insertion rules, or a sprint review.
3. **Docs-as-code, requirements changed only by PR (A Principles 2–3) vs "Asana notes are the contract" (B SHARED-CONTEXT §4; PROCESS_FRAMEWORK "Communication Rules").** Two incompatible definitions of where the requirement *is*. A's is auditable and diffable but heavyweight; B's is where the pipeline actually reads (the coordinator reads Asana notes, not branch files — requirements-agent.md is explicit that a scope doc without the notes is an *incomplete handoff*).
4. **"AI review never counts toward required approvals" (A Human-in-the-loop rule 1, Phase 6 step 2) vs B's three specialized AI reviewers as the entire review layer.** Same axis as #1 but broader: B has *more* review than most teams (security + perf + user-value + UX QA) and zero of it counts under A's rules.
5. **"0 failing tests; coverage ≥ threshold" quality gates (A Phase 7) vs B's stub test targets accepted as "a gap to note, not a FAIL" (qa.md § "Infrastructure features," item 3).** Under A's gates, every B release since 0.5.0 would be blocked. B's implicit position — agent QA + human device testing substitute for automated suites — is a philosophy clash, not a tooling one, and B's repeat-incident record (v0.6.11 crash class) is evidence on A's side.
6. **"Read every line… if you cannot explain a line, it does not ship" (A Phase 5 step 7, pairing section) vs B, where no human reads any code before merge.** A's comprehension requirement is the accountability anchor ("the human who merges is accountable"); B relocates accountability to the release gate and the charter. Whether that's a lawful substitution is the deepest open question between the frameworks.
7. **Environment promotion dev→staging→production with staging deployable before Sprint 1 ends (A Phase 3 exit gate, Phase 8) vs B's single build machine, no environments, direct-to-published releases.** B substitutes mount-verify + smoke test + real-device confirmation for staging — arguably stronger per-artifact, but it loses A's rehearse-before-production properties (no restore rehearsal, no canary, no rollback drill).
8. **"The repository is the single source of truth" (A Principle 2) vs B's three-layer separation where runtime state is deliberately NOT in git and intent lives in Asana (PROCESS_FRAMEWORK § "Three-Layer Separation," incident #13).** A's monism would have caused B's layer-mixing incident; B's pluralism would fail A's audit model ("chat threads are not SSOT until committed" — B's STATUS.json is a third category A has no shelf for).
